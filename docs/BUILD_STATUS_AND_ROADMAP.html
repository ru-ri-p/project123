What Attest is, in one paragraph

Attest is a tamper-evident AI audit layer — an SDK and API that records every AI action your product takes as a cryptographically signed, hash-chained, externally time-stamped event that an outsider can verify without trusting you. On the way, it checks each AI output against your own policy and the rulebooks that apply to you, flags or blocks problems, and proposes compliant fixes. It is aimed at UAE regulated finance (DIFC/ADGM) and government.

In plain English Think of a flight recorder for AI. Every time your AI says or does something, Attest writes it into a sealed logbook that can't be secretly edited later — not even by us — and checks it against the rules first. If something's wrong, it says so and suggests the fix. The pitch: "we flagged it, here's the fix, here's proof the fix shipped, and nobody can doctor that history."

02 · What's been built

The system, module by module

Everything below is implemented, tested, and committed. Each block names what it does technically, then in plain terms.

Cryptographic coredone

Technical: one canonicalisation function (shared by write and verify paths), SHA-256 hashing, Ed25519 signatures, hash-chaining of events, Merkle batching, and anchoring each batch to an external RFC-3161 timestamp authority (endpoint swappable via ANCHOR_TSA_URL). A per-event algorithm id allows future post-quantum migration. The verifier never raises on bad input — it reports and continues.

In plain English This is the sealed-logbook machinery. Each entry is fingerprinted, signed, and chained to the one before it, then stamped by an independent outside clock — so any later edit is instantly detectable, and the outside stamp means not even we can backdate or rewrite it.

Events, API & SDKdone

Technical: FastAPI service (16 routers) over PostgreSQL; the Python SDK (v0.2.0) is a thin HTTP client + local policy pre-check + durable offline buffer. The whole integration is one gate() call; sequence numbers are assigned server-side.

In plain English The customer's engineers add one line of code. Everything — checking, recording, sealing — happens behind that single call.

Policy gate & risk tiersdone

Technical: a deterministic verdict pipeline — feature extraction → the customer's own policy (the only layer that can deny) → advisory jurisdiction packs (raise tier, cite the instrument, never block) → a green/yellow/orange/red tier and a compliant/flagged/blocked status. Red + flag on a customer rule is the human-approval gate.

In plain English A traffic light for every AI output. Green = fine, red = stop. Only the customer's own rules can actually stop something; our regulation libraries can warn and cite the law but never block the business.

Remediation loop (deterministic + model rewrite)done

Technical: flagged/blocked verdicts carry a deterministic fix plan (redact PII to labelled tokens, soften promissory phrasing); for judgement-call violations a model drafts a rewrite that the same deterministic engine re-judges before offering ("the model proposes, the gate disposes"). Reclassifications require human confirmation. The fix is sealed under a plan-hash; applying it and re-gating compliant closes the flag as REMEDIATED.

In plain English It doesn't just say "this is wrong" — it hands over a corrected version, and proves the correction itself was checked, not just trusted. When the fix is applied, the original problem is marked closed in the sealed record.

SDK per-tier auto-remediationdone

Technical: auto_remediate={"yellow":"auto","orange":"auto","red":"human"} — the customer chooses, per tier, whether the SDK applies a complete gate-verified fix itself (and re-gates in the same call) or leaves it to a person. Never crosses three lines: blocked verdicts, human-confirmation rewrites, incomplete fixes.

In plain English The client decides which problems fix themselves automatically and which must wait for a human to approve — serious things always wait for a person.

Content encryption, customer-key & consentdone

Technical: AES-256-GCM content encryption; customer-key mode wraps content keys to a public key the org holds, so stored content is dark to Attest until released through a scoped consent ceremony (generate keypair → enable → approve/deny per request). Requests and answers are themselves recorded.

In plain English The client can lock their content with a key only they hold. We store it but can't read it — until they explicitly unlock one specific record for a specific reason. This is the rarest thing we do; no competitor pairs it with the sealed logbook.

Evidence export & offline verifierdone

Technical: /v1/evidence/{trace}/export?format=zip produces a self-contained bundle (events, manifest, compliance summary, public key, a standalone verify.py, README) that re-checks every hash, signature, chain link and anchor offline.

In plain English One click produces a package a regulator runs on their own laptop, with no access to our systems, to confirm the records are genuine and unaltered. This is the product's whole point.

Human authentication (users, roles, passwords, login)done

Technical: users with roles (admin/officer/viewer); email + password login with Argon2id hashing, durable per-account lockout, and a one-time emailed code for first sign-in and reset; 256-bit session tokens stored hashed and revocable; a styled /login page and a session-aware console. No user enumeration; timing-equalised failures.

In plain English Real people log in with email and password; the system is built so a stolen database or a guessing attack gets nowhere. The one catch: sending the login-code emails needs a domain we don't own yet (see Issues).

Named-person approvals & the officer work queuedone

Technical: a signed-in officer resolves approvals; the sealed event records their verified identity (user id + display name, PII-safe) vs a name merely asserted over the API key. The console opens on a work queue: approvals waiting, rewrites awaiting confirmation, and flags awaiting remediation, with one-click approve/deny.

In plain English When a compliance officer approves something, the record names that real person — exactly the accountability a regulator wants. And their day starts on a "here's what's waiting for you" screen, not a data dump.

Policy dry-run previewdone

Technical: /v1/policies/preview judges a sample output against the active, a named, or a candidate ruleset using the exact gate pipeline, recording nothing — surfaced as a "Test a rule" box in the console.

In plain English An officer can paste a sample and see what the rules would do, before relying on them — nothing is recorded, so it's a safe sandbox.

Regulation packs & watch, security hardeningdone (with caveats)

Technical: jurisdiction rule packs (DIFC-focused) with a scheduled regulation-watch (pacing, retirement, hand-attestation for Attest's own team); security response headers (CSP, HSTS, X-Frame-Options, nosniff, Referrer/Permissions), Dependabot, pip-audit, and a SECURITY.md (posture, data-residency answer, incident runbook).

In plain English The regulation libraries exist and refresh themselves carefully, and the web layer is hardened against common attacks. Caveat: the rule content is drafted from public sources and not yet lawyer-reviewed — it's labelled accordingly and can never block a client.

03 · Testing & QC

How we know it works

  • 280 automated tests pass, most written as attacks (cross-org reaches, session theft, code brute-forcing, user enumeration, tamper attempts).
  • Break-and-detect tamper tests (21) pass — altering any record is detected and the exact record named. This is a CLAUDE.md rule before every commit.
  • 27/27 dress rehearsal, exit 0 — the full customer-pilot path on synthetic orgs: verdicts, the sealed chain, the remediation loop, customer-key consent, an outage drill, and an evidence bundle verified offline ("ALL EVENTS VERIFIED").
  • A concrete synthetic trace (a TradeEasy-style brief leaking a client email) was run end-to-end: flagged orange citing DIFC Reg 10 → redacted fix → re-gate compliant → all four sealed events verified.
In plain English We didn't just build it and hope. We ran fake-but-realistic data through the real system, tried to break and tamper with it on purpose, and it held — including the all-important test where an outsider re-checks the sealed records and confirms they're genuine.
The one QC step left: this all ran on our machines. The final gate before a real customer is running the same dress rehearsal against the live production server after it's deployed — expecting the same 27/27. That is the go/no-go for sending the TradeEasy package.

04 · How deployment works

The pipeline, and why production is behind

Technical: work lands on the feature branch → merged to main → a GitHub Action mirrors main to the deploy repo (ru-ri-p/project123) → Render builds from there with autoDeploy off, so a human clicks Manual Deploy. The mirror was broken by an expired token and is now fixed and green. But the manual Render deploy has not been done since the pre-authentication commit, so production is running old code: no auth, no work queue, no rule-preview, no security headers, SDK 0.1.

In plain English Our code travels through three stops before it's live, and the last stop is a manual button in Render that hasn't been pressed in a while. So everything built in the last several weeks is written down and ready, but the public server is still running the older version. Pressing that button (plus two small settings) is the single most important next action.

08 · Glossary

Jargon, decoded

Hash / hash-chain
A fingerprint of data; chaining each entry's fingerprint into the next means you can't change an old entry without breaking every one after it.
Ed25519 signature
A digital signature anyone can check with a public key but only we can produce — proof an entry is genuinely ours and untouched.
Merkle batch
A way to bundle many entries under one fingerprint so a whole batch can be proven at once.
RFC-3161 / external anchor
An independent, outside time-stamp service that "notarises" our records — so not even we can backdate or rewrite history.
Customer-key mode
The client encrypts content with a key only they hold; we store it but can't read it until they unlock a specific record.
The gate
The single function that checks, records, and seals an AI output. The whole integration.
Tier (green/yellow/orange/red)
The risk level of an output. Red is most serious; only the client's own rules can actually block.
Remediation
The suggested fix for a flagged output, plus proof the fix was itself checked and shipped.
Dress rehearsal
A one-command script that runs the whole customer journey on fake data and checks 27 things — our go/no-go test.
SCITT
An emerging industry standard for exactly this kind of signed, transparent, independently-verifiable record — worth aligning to.
KMS / HSM
Hardware-grade secure key storage; where our signing keys should live in production (currently on disk for testing).
DIFC Reg 10 / CBUAE guidance
The UAE rules that create demand: they require accountable, demonstrable records of what AI systems do.
