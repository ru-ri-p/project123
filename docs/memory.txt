WHAT ATTEST IS (one paragraph, for a cold start)
------------------------------------------------
A tamper-evident AI audit layer for UAE regulated finance. Every AI action is
canonicalised, SHA-256 hashed, hash-chained, Ed25519-signed, Merkle-batched and
anchored to an external RFC-3161 timestamp authority — so not even Attest can
rewrite history. Customer content can be encrypted under customer-held keys
("dark at rest"); Attest sees it only through a consent ceremony the customer
approves, and every step of that ceremony is itself recorded in the same
tamper-evident chain. On top of provenance sits a policy layer: the institution's
own policy (decisive) plus jurisdiction rulebooks (advisory).

STANDING RULES (from CLAUDE.md — do not violate)
------------------------------------------------
- Never commit secrets. keys/, .env, *.pem, *.key are gitignored.
- ONE canonicalisation function (app/crypto/canonical.py), shared by write and
  verify paths. Never fork it.
- The break-and-detect tamper test must pass before every commit.
- A verifier NEVER raises on bad input — it reports failure and continues.
- Config from environment variables only.
- SHA-256 / Ed25519 / AES-256-GCM, with a per-event algorithm id for migration.
- Dev key custody is DISK for synthetic data only. Production = KMS/HSM.
- Attest proves records are UNCHANGED, never that outputs are LAWFUL. Never
  claim it "makes you compliant".

10. Regulation auto-update (the watcher)
   - app/services/reg_watch.py + scripts/watch_regulations.py + a daily Render
     cron (attest-regwatch, 03:00) + a Regulation Watch screen in /admin.
   - THE DESIGN POINT: nothing is generated. The pipeline only CONFIRMS claims a
     human already wrote into a pack, against the official text they cite.
     Three gates, all must pass or it is quarantined:
       1 PROVENANCE  — HTTPS fetch from the URL registered against the pack;
                       the exact text is snapshotted and hashed and retained, so
                       any published claim stays re-checkable later.
       2 VERBATIM    — the claim must appear literally in that snapshot
                       (whitespace/case normalised only). No paraphrase, no
                       inference. This is what makes fabrication structurally
                       impossible rather than merely unlikely.
       3 REPRODUCIBLE— extraction repeated 3x; only identical results pass.
   - Auto-published: confirming a rule's `provision_candidate` when it is found
     verbatim. Published as a NEW pack version (suffix +svYYYYMMDDHHMMSS) with
     verification_status = source_verified — a status that means "mechanically
     checked against the official text" and must NEVER be read as, or promoted
     to, counsel_reviewed.
   - NEVER auto-published: new obligations, changed tiers, altered meaning, or
     anything at all when the source text drifted. Those quarantine, because
     deciding what a changed regulation MEANS is judgement.
   - Also detects: dead/moved sources (HTTP >=400) and fetch failures, both
     surfaced loudly rather than ignored.
   - REGWATCH_AUTO_PUBLISH=false turns publishing off while still monitoring.

Two bugs of mine that the sweep exposed, both now fixed:
  1. EVERY status >=400 was reported as "may have been withdrawn". For a 429 that
     is simply false. Now classified: 404/410 = source_gone (evidence about the
     instrument); 401/403 = source_blocked (bot protection, says nothing about the

  2. Raw response bytes were hashed, so CSRF nonces, scripts and rotating banners
     read as "the law changed". Now only VISIBLE TEXT is hashed (scripts, styles,
     comments and tags stripped), AND drift must be confirmed on two consecutive
     sweeps before it is reported (regulation_sources.pending_hash). A watcher
     that cries wolf daily is one nobody reads.

SESSION: 2026-08-04 (cont.) — "space the sweep out"
--------------------------------------------------------------------------------
Acting on the note above: difc.com's 429 was not a fluke, it was us asking two
packs' worth of pages from one host in the same instant. Spacing now happens in
two places, because "all at once" was true in two different ways.

WITHIN A RUN
  - HostPacer keeps a minimum gap between requests to the SAME host
    (REGWATCH_HOST_DELAY_SECONDS, default 6). Per host, not global: the
    constraint belongs to the site, and slowing every request to protect one
    would make the sweep needlessly slow.
  - build_fetcher retries 429/500/502/503/504 (REGWATCH_MAX_RETRIES, default 2),
    honouring the host's own Retry-After, capped at 60s — a cron holding a
    database session must not sleep for an hour. A malformed (HTTP-date)
    Retry-After falls back to exponential backoff rather than breaking.
  - Still HTTPS-only. Pacing did not weaken Gate 1.

ACROSS RUNS  (new: regulation_sources.next_check_at, migration c7d3e4f81a25)
  - A run checks only sources that are DUE, at most MAX_SOURCES_PER_RUN
    (default 3). Interval REGWATCH_CHECK_INTERVAL_SECONDS, default 24h.
  - next_check_at is booked BEFORE the fetch, so a source that fails is still
    put to the back of the queue. A failed source that stayed due would be
    retried on every run — the same hammering, one level up.
  - NULL (never checked) sorts first, so a newly registered pack is picked up on
    the very next run instead of waiting out an interval it was never part of.
  - run_watch now returns sources_total / sources_deferred / next_due_at, and
    both the dashboard toast and the cron log print them. "Checked 3" with no
    denominator reads as "everything is up to date", which would be a lie.

A side benefit that was really the point: "Run sweep now" no longer holds a
database session open for minutes while it sleeps. The regwatch E2E was in fact
failing on a 30s timeout before this — the pacing alone had made the button hang.

  scripts/watch_regulations.py (cron) defaults to limit=0 = everything due,
  since a cron has the wall clock and the per-host pacing keeps it polite.

Tests: 4 new in tests/test_reg_watch.py (only-what-is-due, not-rechecked-until-
due, a-failed-source-is-still-scheduled, never-checked-sorts-first) on top of the

SESSION: 2026-08-04 (cont.) — a screenshot found a real bug
--------------------------------------------------------------------------------
Founder sent the deployed Regulation Watch screen. It showed ADGM's OLD, dead URL
(/legal-framework/legislation) still being fetched, long after we corrected it to
/legal-framework. Confirmed locally: TWO source rows for adgm_dp_regs.

CAUSE: register_sources walked EVERY pack row, and each published version is its
own row. So the previous version kept re-registering its dead link on every
sweep. The watcher would report that 404 daily, about a URL nothing cites — the
exact crying-wolf failure the drift confirmation was built to avoid.

FIX (migration d8e1f2a63b47, regulation_sources.retired_at):
  - current_pack_urls() resolves the LATEST version per pack code. That is the
    only thing that decides what gets fetched.
  - register_sources now SYNCS rather than only adds: registers what is missing,
    retires anything no pack cites any more, and un-retires a URL if a pack
    cites it again (a reverted correction must still be fetchable).
  - RETIRED, NOT DELETED. The snapshot is the evidence behind anything published
    from that source and has to stay re-checkable by an auditor who does not
    trust us. Retired rows stay visible in the ops table, greyed, marked NO
    LONGER CITED, sorted last, never fetched, excluded from every count.
  - Verified against the real data: the dead ADGM URL retires, the corrected one
    stays live.

ALSO: the STATE chip was rendering the raw Python exception
("HTTPSConnectionPool(host='www.adgm.com', port..."). The stored last_error stays
exact — that is what an engineer needs — but the chip now says UNREACHABLE /
TIMED OUT / TLS FAILED / DNS FAILED / HTTP 429 · RATE LIMITED, with the full text
in the tooltip.
