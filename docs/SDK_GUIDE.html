The Attest SDK, end to end

How the SDK works, every configuration that matters, and in-depth worked examples for the situations you'll actually hit — the happy path, a blocked action, a multi-step pipeline, an Attest outage, and a customer-key deployment.

The mental model

The SDK is three things in one object: a thin HTTP client to the Attest API, a local policy pre-check for speed, and a durable offline buffer so an outage never leaves a hole in your audit trail. You interact with almost all of it through a single method — gate().

The contract is deliberately narrow: Attest reports, your code decides. The gate evaluates an output, records the decision and the output as signed, chained, externally-anchored events, and returns a verdict. It never changes what your application does on its own — with one opt-in exception you configure (auto-remediation, below).

Everything the SDK sends is sealed into a tamper-evident chain. That is the product: not the verdict in the moment, but the provable record of it afterwards.

Install & configure

# the wheel is provided by your Attest contact
pip install attest_sdk-0.2.0-py3-none-any.whl

Create the client once at startup — it holds a local cache, an offline queue and a device key, so it's a long-lived singleton, not a per-request object.

from attest_sdk import AttestClient

attest = AttestClient(
    api_key=os.environ["ATTEST_API_KEY"],   # never hardcode
    base_url="https://attest-api-ipvl.onrender.com",
    auto_remediate={"yellow": "auto", "orange": "auto", "red": "human"},
)
attest.prepare_offline()   # optional: be outage-ready before the first request

The gate call

This is the whole integration. After your model produces an output, pass it to gate() before a user sees it.

result = attest.gate(
    {"output": brief_text},        # the AI output (+ any context) to judge and record
    action="model_completion",       # what happened, in your vocabulary
    trace=None,                       # group multi-step stories (optional)
    on_error="flag",               # outage behaviour: "flag" keeps serving, "raise" throws
)

Sequence numbers are assigned server-side — you never manage them. Put the user-facing text under "output"; add a "classifier" field when your own pipeline already knows the output is individualised advice, so the advice rules key on it.

Reading the verdict

The GateResult tells you what to do. Four outcomes you handle, plus two conditions from an outage.

compliant serve it flagged allowed, but review / fix blocked withhold; approval needed unevaluated recorded, no active policy yet 
if result.blocked:
    serve("This response is being reviewed before release.")   # approval_id is set
elif result.auto_remediation and result.auto_remediation["applied"]:
    serve(result.auto_remediation["output"]["output"])         # the cured text
elif result.flagged:
    review_queue.put(result); serve(brief_text)               # flagged != forbidden
else:
    serve(brief_text)                                         # compliant / unevaluated

Log result.summary() on every call — a one-line record that makes support conversations trivial. During an outage you'll also see result.offline (the verdict is provisional, from cached rules) or result.buffered (queued to replay), and result.recorded tells you whether the server has it yet.

Fixes & verified rewrites

A flagged verdict carries a suggested fix. Mechanical problems get a deterministic fix (personal data redacted to labelled tokens, promissory phrasing softened), each edit naming the finding it cures. Judgement calls a rule can't mechanically fix get a model-drafted rewrite — which the deterministic engine re-judges and only offers if it now passes. The model proposes; the gate disposes.

if result.flagged and result.has_fix:
    fixed = result.apply_suggestion()        # a copy of the revised payload
    proof = attest.gate(fixed, trace=result.trace_id,
                        remediates=result.decision_seq)
    # proof.compliant → the flag is closed in the sealed history

if result.rewrite and result.rewrite["requires_human_confirmation"]:
    # the draft changed what the output IS — a person confirms, then:
    proof = attest.gate(result.apply_rewrite(), trace=result.trace_id,
                        remediates=result.decision_seq)

The remediates= argument names the flagged decision this output cures; the fix must land in the same trace as the flag, so the flagged → fixed link is part of the sealed story, not an annotation anyone could drop.

Per-tier auto-remediation

You decide, per risk tier, whether the SDK applies a verified fix itself or leaves it to a person. One line, set at construction.

auto_remediate={"yellow": "auto", "orange": "auto", "red": "human"}

With a tier set to auto, a flagged output at that tier whose fix is complete and gate-verified is applied and re-gated inside the same gate() call. You get the final (usually compliant) verdict back, annotated with result.auto_remediation — including output (the cured payload to serve) and remediated_seq (the flag it closed). The original flag stays sealed in the chain; auto mode changes who presses the button, never what gets recorded.

Three lines auto mode never crosses, whatever you configure: blocked verdicts (your own policy denied the action); rewrites marked requires_human_confirmation (the meaning changed — a person confirms); and incomplete fixes (anything unresolved or missing evidence would just re-flag).

Approvals

A blocked verdict names a pending approval in result.approval_id. A compliance officer resolves it — from the console as a signed-in person, or programmatically:

attest.resolve_approval(result.approval_id, status="approved",   # or "denied"
                        approver_id="officer_1", comment="reviewed")

The resolution itself becomes a signed event in the same chain. Resolved in the console by a logged-in user, it records that verified person, which is stronger evidence than a name passed over the API.

Multi-step traces

Each gate() is its own record by default. To tell one story across steps — retrieval, tool call, final answer — pass the trace forward.

step1 = attest.gate({"draft": draft})
attest.gate({"tool": "price_lookup", "result": price},
            action="tool_call", trace=step1.trace_id)
final = attest.gate({"output": answer}, trace=step1.trace_id)

The whole trace replays as one verifiable sequence, and an evidence bundle for it proves the entire chain of reasoning, not just the last line.

Offline resilience

Nothing to build — it's on by default. If Attest is unreachable, gate() does not raise (unless you asked for on_error="raise"): it evaluates locally against cached rules, signs the claim with a per-device key, and queues it durably under state_dir. On the next successful call the backlog is handed over and verified signature-by-signature before anything is recorded.

attest.pending_offline    # events waiting to be handed over; 0 in steady state
attest.flush_offline()    # force a replay attempt; returns how many were accepted
The one thing never buffered: a remediation (remediates=). A "this fixes decision N" claim is only true once the server has checked it against the real chain — queueing it unvalidated would let a dead network mint links nobody verified. During an outage a remediation returns error, and you retry when Attest is back.

Expose pending_offline in your health endpoint; a non-zero value that never drains means the replay path needs attention.

Customer-key & consent

If you'd rather Attest couldn't read your stored content, the consent client sets up customer-key mode: content is encrypted to a key you hold, and stored records are dark to Attest until you deliberately release one.

from attest_sdk import ConsentClient
consent = ConsentClient(api_key=..., base_url=...)
priv, pub = consent.generate_wrapping_keypair()   # keep priv in YOUR custody
consent.enable_customer_key(public_pem=pub)

# later, when Attest requests a specific record for review:
consent.approve(request_id, granular=True)         # releases exactly one record
consent.deny(request_id)                            # Attest reads nothing

Every request and your answer are themselves recorded, so the access history is as tamper-evident as everything else.

Worked use cases

Use case 1 · the core loop

Market briefs that self-heal on the routine stuff

A DIFC market-intelligence desk, yellow/orange on auto, red to a human.
result = attest.gate({"output": brief_text})

if result.blocked:
    publish(HOLD_MESSAGE)                       # e.g. an execute-trade instruction
elif result.auto_remediation and result.auto_remediation["applied"]:
    publish(result.auto_remediation["output"]["output"])  # PII already redacted
else:
    publish(brief_text)

A brief mentioning a client's email is silently corrected and published, its flag-and-fix sealed. A brief that reads as individualised advice, if the rewrite is clean and needs no human confirm, is likewise healed. Anything your policy forbids outright still stops and waits.

Use case 2 · the human gate

A high-risk action held for clearance

An automated action your own policy denies unattended.
result = attest.gate({"output": "execute buy 500 XAUUSD"}, action="execute_trade")
assert result.blocked and result.approval_id

# officer reviews in the console and approves as themselves; or programmatically:
attest.resolve_approval(result.approval_id, status="approved",
                        approver_id="risk.officer", comment="within mandate")

The block, the review, and the named approver are all in one sealed trace — exactly the record a DIFC audit asks for.

Use case 3 · a reasoning pipeline

Prove the whole chain, not just the answer

A retrieval-augmented assistant answering a client question.
t = attest.new_trace()
attest.gate({"query": q}, action="user_query", trace=t)
attest.gate({"retrieved": docs}, action="retrieval", trace=t)
final = attest.gate({"output": answer}, action="model_completion", trace=t)

If the final answer is later questioned, you can show what was retrieved and how the answer followed — a verifiable lineage, not a bare claim.

Use case 4 · surviving an outage

Keep serving, keep the trail

Attest is briefly unreachable during a deploy or network blip.
result = attest.gate({"output": brief_text})
if result.offline:
    # provisional local verdict; the signed claim is queued durably
    publish(brief_text)
# next successful gate() drains the queue automatically; or force it:
sent = attest.flush_offline()

Your product never stalls on Attest, and the audit trail has no gap — the queued events replay, verified, the moment it's back.

Use case 5 · content stays dark

A confidential deployment

A firm that will not let a vendor read client content at rest.
priv, pub = consent.generate_wrapping_keypair()
consent.enable_customer_key(public_pem=pub)
# gate() is unchanged; content is now encrypted to YOUR key at rest.
result = attest.gate({"output": brief_text})
# dashboards still work on signed metadata; content is unreadable to Attest
# until you consent.approve(request_id) for a specific record.

You get the full audit and compliance story with none of the content ever legible to Attest or its host.

Without the SDK

The SDK is a convenience over a plain REST API. Any language can integrate with one POST:

POST /v1/gate
x-api-key: <your key>
{ "action": "model_completion", "output": { "output": "…" } }

# → { "status": "flagged", "tier": "orange", "trace_id": "…",
#     "decision_seq": 3, "suggested_fix": { … }, "approval_id": null }

You lose the offline buffer, the local pre-check and the device chain — but the verdict, the sealed record and the remediation loop all work exactly the same. Questions go to your Attest contact.
